Qwen3.8-Flash-Next · 125B-A6B · one RTX PRO 6000 Blackwell, 96 GB

Three Engines, One Card

The same 125-billion-parameter model, served three ways on one workstation GPU — and, since the first report, a draft head that makes the slowest of them competitive. Speed differs by up to 7.3×. Accuracy does not differ at all.

01How every test here is run

The rules first, because a number without its method is not a result

Two words appear in every table. Prefill is the speed at which the server reads the prompt. Decode is the speed at which it writes the answer, one token at a time. Both are tokens per second. They are different machines doing different work, and almost every disagreement between these three engines is a disagreement about one and not the other.

One engine at a time, on a card that has cooled down

Each arm gets its own container start, behind a lock that makes a second engine impossible while one is measuring. Before every start a settle routine waits for the previous arm's VRAM to be released, then waits for the card to reach 42 °C or below. A hot card clocks lower, so back-to-back arms would measure the order they ran in rather than the configuration under test. Every engine runs under the same cgroup memory cap, so one stack cannot fail differently from another because it was given more room.

One client measures all three

A single AIPerf process drives every engine over its OpenAI-compatible endpoint. Time to first token and inter-token latency are therefore computed the same way for all three, rather than read out of each engine's own log where each would define them slightly differently.

The workloads

No live traffic. Every test draws from one of a few fixed workloads, so a re-run sees the same input. Prompts come from contiguous natural prose or from real LiveCodeBench problems, never from synthetic filler — a corpus that repeats itself feeds a speculative drafter and would be reported as engine speed (section 06).

Provenance records what ran, not what was asked for

Before the first request, each arm records the server's resolved launch flags, the image digest, the model revision and the workload parameters. That distinction has already paid for itself here: a workload file was once silently overriding the environment, so a whole sweep ran identical arms under different labels. Recording intent would have hidden it; recording what the server actually reported did not.

An arm can fail, and failing is recorded

A container restart voids the arm outright — every service is set never to restart, so a restart means it died. An out-of-memory kill is kept as a capacity finding rather than retried until it passes. A thermal throttle voids the arm. In the accuracy runs, items that errored are excluded rather than scored as wrong: counting a killed run's errors as wrong answers once turned a 95% result into an apparent 8%, which would have read as catastrophic quantisation damage instead of an interrupted run.

Runs that were voided are kept, not deleted, and listed with their reasons in the repository beside the ones that count. Section 15 gathers the findings that were withdrawn.

Every number here was generated, not typed

The tables and charts in this report are produced by a script that reads the saved evidence directories and prints every value it drew. Nothing is transcribed from a terminal. That is why a re-scored benchmark cost no GPU time at all: when a scoring bug was found (section 16), every raw response was already on disk, so the fix was a re-score rather than a re-run.

What those placement words mean

The 47.68 GiB lookup table does not fit in VRAM beside the weights, so each engine puts it somewhere else — and that choice is most of what separates them. Host RAM, resident copies the table into ordinary system memory at load time: fastest to read, and it costs you 48 GiB of RAM. NVMe with io_uring leaves it on the SSD and fetches rows through the kernel's asynchronous I/O interface, which lets many reads be in flight at once instead of blocking one at a time. Disk with O_DIRECT also leaves it on the SSD but bypasses the operating system's page cache entirely, reading straight into the engine's own buffers — no double copy, no cache to compete with the weights for RAM, and no help from the cache either.

So llama.cpp trades RAM for speed, and the other two trade speed for RAM. Section 09 measures what that trade is actually worth, and section 10 measures a fourth option.

The one controlled pair: SGLang and FreeToken run the same files at the same revision. Differences between those two are the engine and its kernels, not the weights. llama.cpp cannot be brought into that comparison — no engine loads both formats, so that axis is confounded permanently and is reported as a stack difference, never as a quant result.

03Speed against context

2K to 261K tokens — the main result

How this test runs

Fixed input lengths, a pinned 2,048-token output, one request at a time, three repeats per cell. Thinking mode off on every engine, so completion tokens are answer tokens and the lengths are comparable. Prompts are sampled as contiguous slices of natural prose; the alternative corpus was measured at 31.8–67.2% repeated 8-grams and disqualified.

Three different shapes, not three speeds. llama.cpp decays on both axes — decode falls from 101.9 to 20.2, a 5× collapse across the ladder. FreeToken is almost flat: 100.1 down to 94.8 over 127× the context, and its prefill doubles with length as fixed per-request costs amortise. SGLang shows no decay at all — 191.5 at a quarter of a million tokens is the same as it managed at 128K.

The draft head does not just lift llama.cpp — it changes its shape. With the head on, decode goes 126.8, 125.0, 100.0, 100.8, 100.3 across the first five rungs: it drops once and then holds level with FreeToken, where the undrafted line is still sliding. The gap widens the whole way — 2.9× at 128K and 3.0× at the top rung, 61.4 against 20.2. Speculation is worth most exactly where the engine was weakest, because a drafted token costs the same whether the context behind it is 2K or 254K.

The one place it does give way is that last rung: the flat stretch breaks and MTP falls from 100.3 to 61.4. Even there it is three times the undrafted build, but a quarter-million tokens of context is finally enough to cost the drafted path something too.

About that top rung. It is 259,584 tokens, not 262,144, because the prompt and the answer share one window: this workload asks for a 2,048-token answer, so that is what is left for input. An earlier version of the ladder asked for 261,120 and 2,048, which overruns the window — SGLang and llama.cpp refused the request outright, while FreeToken served it anyway. Published as-is it would have read as a capability difference when it was one engine being lenient about an invalid request. The rung was re-derived and re-run on all four arms.

The crossover: FreeToken starts slower than llama.cpp at 2K (1,525 vs 1,869 prefill) and passes it before 8K, ending 2.4× ahead at 128K. Any comparison taken at one prompt length would have reported a different winner.

A withdrawn result, and why it was wrong

An earlier draft of this report carried an output-quality verdict in that last column, marking two of the three stacks measured then degenerate for emitting repetition loops, and called the gap between them the most interesting signal here. That was an artifact of our own measurement, and it has been withdrawn.

Pinning output length requires ignore_eos — the model is forbidden to stop until it has produced exactly 1,024 tokens. All sixteen responses per cell have no natural finish reason; not one of them stopped on its own. Forced past the end of its answer, a model emits filler, and the two kinds we saw were exactly that: one stack repeated the empty turn marker <|im_start|><|im_end|> up to 103 times, and both restarted the answer, re-emitting class Solution: five times over.

A checker counting duplicate lines then scores that filler as a repetition loop. It was measuring the harness, not the model — and the apparent difference between the stacks is most likely how each one renders forced generation past end-of-turn, a detokenizer difference, not a reasoning one. The checker now detects ignore_eos and withholds a verdict instead of issuing one.

The general lesson is worth more than the retracted finding. The flag that makes a speed comparison fair is the same flag that makes the output unjudgeable. Speed and quality cannot be read off one run: quality has to be measured where the model is allowed to stop when it is finished — which is what section 08 does.

New here: n-gram speculation's benefit is a property of the workload, not the engine. The first report measured the n-gram drafter's average rate; what it could not see, with one corpus, is that the mechanism does not engage at all on the other one. On natural prose ngram-mod generated zero drafts — the flag was accepted and the mechanism never engaged, because it drafts by finding a 24-token exact match and prose at ~1.5% repeated 8-grams never supplies one. On real code the same flag produced 59 drafts at 37.6% acceptance and +6.8% decode at one request.

This is why the corpus audit mattered. The obvious alternative corpus measures 31.8–67.2% repeated 8-grams; benchmarking a drafter on it would have produced a large, real, reproducible number that measured the corpus and reported it as engine speed.

NEXTN and MTP are the same idea — and SGLang had it working all along

The checkpoint ships one extra layer trained to guess the next few tokens. SGLang calls running it NEXTN; llama.cpp calls it draft-mtp. Same layer, same trick, different name. SGLang has been using it in every number in this report — which is part of why its decode is flat across the ladder — while llama.cpp could not load the file at all until the build in section 11.

That is worth saying plainly, because it means the engines were never on equal terms: one was running the model's own accelerator and the other was not. Section 11 is what happens when both do. It also means EAGLE and the like are not in play here — nobody needed to train a separate draft model, because this checkpoint brings its own.

One thing not established, and one now settled

The NEXTN pair is confounded. The speculation-off arm ran at a smaller KV pool fraction than the speculation-on arm, so those two differ in more than the drafter. At one request the pool should not move decode, but this pair does not prove it, and +58.9% is not a publishable speculation delta until the arms match.

The llama.cpp draft head was blocked, and is not any more. The published file holds one layer and nothing else — 32 tensors, all from layer 48, sharing the base model's embedding table — and llama.cpp loads a draft as if it were a complete model, so it refused the file for having no embedding table of its own. The layer is not inside the main weights either: both quantised files stop at layer 47. Two upstream pull requests would fix that and neither has merged. Section 11 gets it running anyway, from the checkpoint publisher's own fork, and measures what it is worth.

08Does the cheaper quantisation still think?

Exact-match accuracy — validated against a published number first

How this test runs

GSM8K (1,319 problems) and MATH-500, scored by exact match — the final number for GSM8K, a symbolic checker for MATH-500. No model is ever used to judge another model's output. Each engine runs at its best-known configuration with the same non-thinking sampler as the speed runs, and every prompt, raw response, extracted answer and verdict is written to disk so a score can be recomputed without re-running the model.

What this can and cannot answer

It cannot measure absolute quantisation damage. A 16-bit copy of this model is roughly 250 GB against 96 GB of VRAM, so there is no full-precision reference on this machine. Nothing here can say "this format loses N points". What it can measure is disagreement: where two stacks differ, by how much, and whether the difference changes an answer.

One external anchor exists. The NVFP4 checkpoint ships its own published GSM8K score of 97.27%, measured on these exact files. Reproducing it is the first gate — if our pipeline cannot, nothing downstream of it is trustworthy.

The gate passes. Scored end to end through this pipeline, the NVFP4 checkpoint returns 95.22% on GSM8K against the published 97.27% — our non-thinking sampler against their longer-budget one. The pipeline reproduces the published number, so the rest of this section can be trusted.

Scoring is deterministic and re-runnable. Because every prompt, raw response, extracted answer and verdict is written to disk, any figure in this section can be recomputed from the stored evidence without putting the model back on the GPU — a scoring change costs a re-score, never a re-run.

{{ACC_BLOCK}}

All four arms land within eight-tenths of a point of each other on both benchmarks. Nothing in the speed table — where the spread reaches 7.3× — has any echo here.

The comparison that actually has power

Because the scores land so close together, comparing the two percentages directly settles nothing — and it throws away most of the evidence. Every stack answered the same problems, so the items they both got right, and the items they both got wrong, say nothing about which one is better. Only the items where they disagree carry any information. The table below lays out exactly that split, pair by pair.

How to read the table

Each row pairs two stacks on one benchmark and sorts every question into four buckets: both right, both wrong, only A right, and only B right. The first two buckets are the agreements — they are large, and they are ignored. The question is whether the two disagreement buckets are lopsided. If one stack is genuinely better, it should win noticeably more of the items where the two differ.

McNemar's test is what turns that into a number. It asks a single question: given this many disagreements in total, how surprising is the split between them? It is the same reasoning as a coin flip — 30 disagreements splitting 16/14 is what you would expect from chance, while 30 splitting 28/2 is not. The p-value is the probability of seeing a split at least this lopsided if the two stacks were in truth equally good. A small p (below 0.05) means the imbalance is hard to explain as luck; a large p means it is entirely ordinary. Only the two disagreement columns feed the calculation.

{{PAIRED_BLOCK}}

Nine comparisons, nine nulls. Every pairing on both benchmarks comes back indistinguishable, with the smallest p-value at 0.30. The stacks disagree on only 2–5% of items, and those disagreements split near-evenly every time.

The clearest sign that this is noise rather than a small real effect is that the ranking flips between the two benchmarks. FreeToken leads on GSM8K and comes last on MATH-500; SGLang does the exact opposite. A genuine quantisation deficit does not reverse itself when the questions get harder.

The aggressive quantisation carries no measurable penalty here. The checkpoint with 44.6% of its parameters at about 3.4 bits scores within half a point of the one that leaves attention, gates and shared experts at full precision — ahead of SGLang on GSM8K, behind it on MATH-500, neither by enough to matter.

What that does and does not establish. With 22–41 discordant items per pair, this rules out a gap larger than roughly a point and a half. It is not proof of equality, and both benchmarks sit near this model's ceiling — 92–96% correct is exactly where a quantisation difference is least likely to surface.

These are deliberately modest tests. GSM8K and MATH-500 are short, standard, well-understood suites, and 1,819 items per stack is what fits in an evening: the whole section above is 5.0 GPU-hours, between 0.5 and 2.1 hours per arm. Sharpening the result means more disagreements, and more disagreements means proportionally more questions — resolving a half-point gap rather than a point-and-a-half one needs roughly ten times the items, which is on the order of 50 GPU-hours, or two days of continuous running before any repeat at a second seed. That is a reasonable thing to spend if a difference is suspected. Nothing here suggests one is.

The test with something left to reveal is long-context retrieval — which has been run on one engine, below, but not as a three-way comparison.

09Why --load-mode none, and not mlock?

A viewer's question, answered with the five modes worth measuring

What was known before this test

This revises a result in the first report. That one measured memory placement as mmap against RAM-resident and found resident 1.87× faster on prefill. That measurement was correct for the configuration it ran in, and the configuration has since changed — which is exactly what this section is about.

The llama.cpp build in this study offers six loading modes: auto, none, mmap, mlock, mmap+mlock and dio. The headline runs use none — copy the host-side tensors into ordinary RAM rather than memory-mapping the file — for two reasons. The loader itself warns that keeping tensors on the CPU under mmap is "not the fast path" and suggests none. And an earlier controlled pair measured it: 1.87× prefill over mmap at identical placement, decode unchanged — a placement, it turns out, that matters: that pair computed 23 expert layers on the CPU, which the headline no longer does.

What had never been run: mlock and mmap+mlock, which pin the mapped pages so the kernel cannot evict them.

All five on the same image and placement, ubatch 1024, real coding prompts at 8K and 32K. The pinning arms run under a host-memory guard, because the llama.cpp container has no memory cap of its own and pinning the whole mapping could exceed RAM — an out-of-memory there is a capacity finding, recorded rather than retried.

10Reading the lookup table straight from disk

llama.cpp PR #28136 — a placement arm for machines without the RAM

How this test runs, and what it is not

An open pull request adds a direct-read mode for the lazy PLE path: when the 47.68 GiB table is left on disk rather than loaded, its rows are fetched with explicit reads instead of demand paging a memory map. Its author reports large cold-prefill gains on a small unified-memory machine.

This does not touch the headline configuration. The headline keeps the table resident in host RAM (--load-mode none); the direct-read mode only applies when the table is not resident. It is the arm for a machine with a fast SSD and not enough RAM — a placement-study result, never a replacement for the resident baseline.

Built as a separate image tag, with the shipped build untouched as the control. One caveat governs the whole section: the shipped image and the pull request are separated by 44 upstream commits and a different CUDA toolchain, so a difference between them is not necessarily the pull request. Isolating it would mean building the request's own base commit as a third tag; that build was queued and never ran. Then lazy off, on, and on-direct under mmap at 8K and 32K, and — because the newer build turned out faster under mmap — the same build at the resident headline configuration, to separate the build from the placement. These are warm-page-cache numbers — the pull request's headline is cold prefill, which needs the page cache dropped between runs and is a follow-up.

11The fastest speculation this model ships

Multi-token prediction — the checkpoint author's own claim, tested

The claim, and how it is built

The people who publish this checkpoint claim multi-token prediction makes it 1.3 to 1.7× faster with no accuracy degradation, and they name this exact card: 170 tokens per second against a 100 token baseline. 12How hot does it actually get?

Temperature, power and clocks while the card is working

Where these numbers come from

Every arm in this study writes a GPU trace beside it — temperature, power, clocks, and the card's own throttle flags, sampled every five seconds — because a benchmark on a desk-side machine is worthless if the card was quietly slowing itself down. That data was collected for guard-rail reasons and is read here as a result in its own right.

Only samples where the GPU is actually busy are counted. Including the idle stretches between requests would reward whichever engine spends longest booting, which is the opposite of the truth.

{{THERMAL_BLOCK}}

Why the fast engine is also the cheap one to run

A GPU under load draws roughly its working power whatever it is doing; it does not draw less because the work is easy. So the energy a request costs is mostly how long the card is held, and finishing sooner is the only real lever. That is why the efficiency spread here (8.9×) is far wider than the power spread (about 1.4×, 358 W against 489 W).

At one full-window request an hour, the slowest stack costs roughly 32 W averaged over that hour against the fastest stack's 4 W — on a machine that idles at about 6 W between requests. Over a working day of that duty cycle the difference is on the order of 0.2 kWh, which is small in absolute terms and completely changes the shape of the bill once the machine is shared, rack-mounted, or metered. The engine that answers fastest is not merely nicer to wait for; it is the one that leaves the card free.

Derived from the traces the harness already writes: median power over busy samples, times time-to-first-token plus decode time. It is an estimate, and the ranking is what it supports.

13The cost nobody benchmarks: starting up

Time from cold container to a served answer, repeated

Why measure this at all

Every other number here assumes the server is already running. On one workstation it is not: you start it when you sit down, and you restart it every time you change a flag. Nobody publishes that cost, and on this box it varies by more than an order of magnitude between engines.

Three or four boots back to back per engine, every attempt reported rather than an average. The page cache cannot be cleared without root, so the first attempt is the coldest and later ones read from RAM; that spread is the cache effect and it is part of the result, not noise to be smoothed away.

14Resizing the cache without restarting

FreeToken's live pool rebuild — and what KV size actually buys

What this is

FreeToken can resize its KV, expert and state pools on a running server (ft ctl cache --kv N, or a POST to its rebuild endpoint), with no restart. That is worth having on its own — but it is also what makes the question underneath cheap to answer. How much KV cache does a workload actually need? Normally that costs one full model load per setting, on the engine whose load is the most expensive here. Live resizing turns it into four requests against a single server.

One prompt, built once and reused at every size, so the pool is the only variable. Each size is requested through the engine's own client, which converts tokens into the pool's page unit against the live geometry, so the size actually applied is read back rather than assumed — it matched the requested size exactly at every step. Every request carries a unique prefix, because an identical repeat is answered from the prefix cache: an earlier pass without that marker read 4.5 s where this one reads 9.0.

15Would this run on a smaller card?

The VRAM ladder, revisited with the draft head — a viewer's question

Where this comes from

A viewer of the first report asked about a 24 GB card with 64 GB of system RAM. The first report's ladder answers the VRAM half of that — it runs this model from an 8 GiB card down to no GPU at all — but it predates multi-token prediction working here, and section 11 measured the draft head only on the full 96 GB card, where it is worth 1.6×. Whether that holds on a small card is a different question, and the answer turns out to be no.

A helper holds GPU memory so the 96 GB card presents a smaller pool, and each tier keeps the expert offload the first report chose for it — from 48 of 48 expert layers on the CPU at 8 GiB, down to none at 96 GiB. Only the draft head changes between arms.

The viewer's questions, answered

"I have an RTX 4090 with 24 GB of VRAM — will this model run?" Yes, at about 35 tokens per second. At a 24 GiB budget the model serves at 34.7 tok/s decode on a 2,048-token prompt, with 42 of its 48 expert layers computed on the CPU. That is roughly a third of what the same model does with the whole 96 GB card (99.8 tok/s), and it is entirely usable.

"Should I turn on multi-token prediction to speed it up?" No — on a 24 GB card it makes things 3.4× slower (10.2 against 34.7 tok/s). The 1.3–1.7× speed-up the checkpoint's publisher advertises is real, but only when every expert sits on the GPU. Putting the draft head on the CPU instead does not rescue it either.

"But I only have 64 GB of system RAM — does that still work?" Yes. Measured in a container hard-capped at 64 GB, and again at 56 GB to leave room for an operating system: 34.4 and 34.7 tok/s, the same speed as with the whole 91 GiB of this box. One flag makes the difference — --lazy-mode on, which reads the 27 GiB lookup table from the SSD instead of holding it in RAM. With it the server uses about 3 GiB. Without it the model still runs at the same speed, but streams itself off the disk continuously to stay under the limit.

The MTP setup, exactly as run

Build: llamacpp-mtp:d1a92352, built from danielhanchen/llama.cpp branch qwen4exp/mtp — the checkpoint publisher's own fork, because the draft head is in no llama.cpp release. The MTP-off baseline runs the same image, so the build is never a variable between arms.

Draft head: mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf — 2.6 GiB, Q8_0, 32 tensors, all of them layer 48, sharing the base model's embedding table. --spec-type draft-mtp, --spec-draft-n-max 5, and --n-gpu-layers-draft at 99 for the "on GPU" arm or 0 for "on CPU". Acceptance at the 24 GiB tier ran 49–74%.

Everything else held fixed: UD-IQ4_XS, the lookup table on the CPU (-ot per_layer_token_embd=CPU), --load-mode mmap, microbatch 512, a 4,096-token context, one slot, one request at a time, 2,048-token LiveCodeBench prompts with 256-token answers, thinking off. --n-cpu-moe is the only thing that changes with the tier, and it takes the value the first report's ladder chose for that tier.

One caveat that applies to every arm here: this build reads the on-demand tensor flag under a different name than the harness sets (section 10), so all of these ran at the build's default, auto. Both arms of every pair carried it, so the comparison holds, but these are numbers for a lookup table streamed from SSD, not held resident.

Known limits of this comparison

The quantisation axis is confounded and always will be. No engine loads both formats, so "which quantisation is better" is not answerable on this hardware. Only "which stack answers better" is.

The 8-bit KV cache is untested directly, though the accuracy result is reassuring. SGLang runs an 8-bit KV cache with a defaulted scale and FreeToken a 16-bit one, on the same checkpoint; they are statistically identical on both benchmarks. That is encouraging but not a measurement of the cache: it is confounded with the engine, and neither benchmark uses enough context for cache precision to bite. Measuring one engine both ways, at length, is the outstanding work.

Speculation availability is welded to engine choice. SGLang has a native draft head, llama.cpp has model-free n-gram lookup and, on an unreleased fork build, the checkpoint's own draft head (section 11), FreeToken has nothing. Every decode number is the engine and whatever drafter it happens to offer.

All three engines run unreleased code. That is a fact about a model this new, and it belongs in any reading of these numbers.

Corrections made during this study

Six findings were corrected or withdrawn after checking, and are recorded here rather than quietly fixed.

An output checker read the wrong path and marked every single-request run degenerate without ever opening its saved responses — 71 KB of good output per run went unread because the file it wanted sits at the top level for a single cell and one directory down for a sweep.

An output-quality verdict was measuring our own harness (section 05). The finding it produced was withdrawn entirely.

A speculation comparison ran at the wrong input length, comparing 32K against 2K and reporting the difference as a speculation gain. Discarded and re-run matched, where the real figure is +6.8%.

A rebuild step failed on our own command. The queue that was to rebuild FreeToken at its newest commit omitted the Dockerfile path; Docker found no file and the step failed in under a second. The queue logged it and skipped the dependent runs rather than retrying, so nothing here is affected. The image was rebuilt on retry with the path corrected, but the accuracy re-run on that newer FreeToken build has not been done, so section 08 reports FreeToken at the older one.

A planned rebuild check was dropped as unusable. Comparing token-for-token output between two builds only works if an engine reproduces itself, and neither of these does: the same request sent twice to one unchanged server comes back different (llama.cpp 13 of 16 prompts, SGLang 16 of 16, with speculation off in both). Rebuilds are checked by scoring answers instead — section 08.

The host reset once, in the middle of a 32K placement arm that read the lookup table lazily from a memory map. The journal ends on routine traffic with no out-of-memory kill, no GPU fault and no panic, so the cause is unknown; the interrupted arm is kept and marked void, and its re-run is scheduled last, under a host-memory guard.
