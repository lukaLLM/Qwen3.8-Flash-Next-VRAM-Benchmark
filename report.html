01How we run every test

The rules come first, because a number without its method is not a result

Two words appear in every table. Prefill is the speed at which the server reads the input prompt. Decode is the speed at which it generates the answer, one token at a time. Both are in tokens per second (tok/s). VRAM is GPU memory. System RAM is the computer's main memory.

The workloads

No test uses live user traffic. Each test uses one of five fixed workloads, so every run of a test sees the same input.

The five workloads, and the sections that use them. Prompt lengths are in tokens.
WorkloadWhat the model receivesUsed in
Speed sweepReal code-problem text (101 LiveCodeBench problems), concatenated and cut to exact prompt lengths from 256 to 245,760. Greedy sampling, a fixed output length, prompt cache off.02, 03, 04, 05, 10
llama-benchThe tool's own built-in prompt and generation tests (pp512, pp4096, tg128).03

Scores come from saved files

Every request writes a result row to disk. We compute each score from those rows with a recorded command. We do not copy scores from terminal output. Each test links its evidence directory.

We read the logs and check the generated text

After each run we read the server log and the model's output. A checker flags runs where the model did not do the workload: tool calls with no executor, stub answers, missing code, or truncated turns. This matters. Three early runs reported plausible speeds — 158, 98, and 105 tok/s — while the model only emitted tool-call syntax and wrote no code. Speed alone cannot show that.

One fresh server for each arm, with a cooldown

Each test arm gets its own server start. Before each start, a settle routine waits until the GPU releases the previous arm's memory. It then waits for the card to cool to 42 °C or less, and holds a floor delay. A hot card clocks lower, so back-to-back arms would measure order, not configuration.

We repeat, and we reverse the order

Two-configuration tests run in A-B-B-A order. Each configuration gets one early and one late position. We report the order effect — for the placement test it was 0.56%. Where sampling adds noise, we run more pairs and report the spread.

We monitor the GPU during every arm

A telemetry watcher samples temperature, power, clock speed, and throttle flags for each arm. DCGM profiling counters record tensor-pipe activity, GPU-memory traffic, and PCIe transfer rates. A thermal throttle voids the arm. A resident arm that swaps to disk also voids. An mmap arm is judged on sustained disk bandwidth instead, because page faults are normal for mmap.

The sampler must match the mode

This model has a thinking mode and a non-thinking mode. The model card gives one sampler for each. Before a workload test, a checker compares the live server against the card for the mode under test, and a mismatch fails the arm.

Every option is checked before the run

Before a server starts, the controller renders the resolved configuration. It compares each option against the arm's intent: tensor placement, context, expert offload, microbatch, batch, parallel slots, GPU layers, loading mode, lazy reads, and KV layout. A mismatch fails the arm before any request is sent.

Why we do not benchmark workloads with greedy sampling

Greedy sampling (temperature 0, top-k 1) promises identical output between arms. On this engine it does not deliver that: with speculation as the only difference, output diverged on the first turn. Speculation verifies several tokens per forward pass, so the arithmetic batches differently, and a near-tie token choice can flip. We therefore compare decode rates under the model-card sampler, and we do not compare total wall time between arms that generate different amounts of text. Fixed-length synthetic sweeps still use greedy with a pinned output length, because there the sampler cannot change how much work is done.

What each run saves

Each arm's directory holds the resolved configuration, the full server log, and the server's reported settings. It also holds GPU and process memory after load, every request row, and the warm-up rows (saved, excluded from scores). Telemetry with a pass/fail verdict and the command that recomputes the score complete the set.

02Why a 125B model fits

51B parameters are a lookup table, not matrix-multiply weights

From the GGUF metadata: 512 experts, 48 blocks, and a per-layer token-embedding (PLE) table with 16 heads of roughly 20 million entries each. That unusually large table explains how the model fits.

Preferred placement in the full 96 GiB run. Context memory is additional to the 87.2 GiB model file; GiB means binary gigabytes.
PartParamsSizeFast placement
Expert weights~120 B60.7 GiBGPU VRAM
PLE lookup table~51 B27.2 GiBSystem RAM (CPU)
262,144-token context—10.3 GiBGPU VRAM

Most model weights feed large matrix multiplications. GPUs are built for that work. The PLE table is different. For each token, the model fetches a small set of rows by address, like records from a very large index. It does not multiply the whole table.

The important placement choice

Expert weights · 60.7 GiB Keep the arithmetic on the GPU

These weights drive matrix multiplications, so GPU compute and VRAM bandwidth help.

PLE table · 27.2 GiB Keep the lookup table in system RAM

The CPU fetches selected rows. This frees 27.2 GiB of VRAM without moving heavy matrix math to the CPU.

The PLE table is a random-access lookup with no matrix multiply. It is the one part of the model that is cheap to move off the card. It is also the biggest part.

With the table in system RAM, decode is 108.5 tok/s. With the table on the GPU, decode is 1.95 tok/s — 55.6× slower. Prefill is 3.4× slower. The memory columns prove the placement moved. The GPU arm holds 27.5 GiB more VRAM, and its host-side model memory falls from 27.2 GiB to 0.4 GiB. The order effect between repeated arms was 0.56%.

Why the fast card loses this one

The result looks wrong at first, because VRAM is faster memory than system RAM. But a lookup gives the GPU nothing to accelerate. Each token fetches a few small rows from the 27.2 GiB table. That is a few kilobytes of useful data and no matrix multiplication. Speed here is set by two things: how far the fetched rows travel, and how often the two processors wait for each other. Bandwidth and compute do not set it.

The prefill and decode columns show the shape of the cost. With the table on the GPU, one decode step takes 513 ms (1 ÷ 1.95 tok/s). That is far longer than any arithmetic in this model needs. Prefill slows only 3.4×, because prefill batches many tokens into one step and pays the per-step cost once. Decode pays it on every single token and slows 55.6×. A per-step transfer and synchronization cost between the CPU and the GPU matches this pattern; a bandwidth or compute limit does not.

This is why the flag matters. The engine stores the table as an ordinary weight tensor. On a card with enough VRAM, a plain -ngl 999 launch can place it on the GPU. The -ot per_layer_token_embd=CPU override exists to prevent exactly that configuration.

Why long prompts stay cheap

Long prompts also use less memory than a conventional 48-layer transformer. Only 12 layers use attention and need a growing key–value (KV) cache. The other 36 use a gated delta network whose roughly 113 MiB state stays the same size as the prompt grows.

04Loading mode: mmap or RAM resident

One flag is worth 1.87× prefill where the RAM allows it

How this test runs

The 48 GiB tier runs again with one change: the loading method for host-side weights. Tensor placement (23 of 48 expert layers in system RAM), context 262,144, and the 512-token microbatch stay identical. mmap runs twice — a first ("cold") pass and a second ("warm") pass — to test whether the operating system's file cache closes the gap. Prompt lengths 2,048 to 131,072; one warm-up plus measured requests per length.

--load-mode none does not mean "do not load the model." It means "use no file mapping." In this report, resident is the short name for this mode: host-side model data is copied into ordinary system RAM.

Concurrency: more total output, slower individual requests

The two KV-cache layouts under test

Unified KV · one shared pool All 16 slots share one 131,072-token pool

Any request can take as much cache memory as is free. Flexible, but requests compete for the same pool, and the bookkeeping covers the whole pool.

Non-unified KV · per-slot The pool is divided: 8,192 tokens per slot, fixed

Each of the 16 slots owns its slice. Requests never compete for cache memory, but no request can use more than its slice.

Same total cache memory in both layouts. The only difference is shared against pre-divided. Every test request here (about 4,000 prompt tokens plus 256 output) fits either layout.

11The configuration that matters

Every flag, and what it is worth here

-ot per_layer_token_embd=CPU   # the 27 GiB lookup table.
                               # On the GPU instead: 55.6x slower.
--load-mode none               # copy host-side weights into ordinary RAM instead
                               # of mmap: 1.87x prefill here. Needs room in RAM.
--tensor-read-lazy off         # 'auto' silently streams any tensor >4 GiB from
                               # disk. The largest PLE tensor is ~25 GiB, so
                               # auto streamed it on every mmap run by default.
--n-cpu-moe N                  # number of the 48 expert layers kept in system RAM.
                               # 0 at 96 GiB VRAM; all 48 at 8 GiB VRAM.
-ub 2048                       # +30.8% prefill vs 512 for +1,058 MiB, measured.
                               # Use 1024 (+17.8%, +352 MiB) if VRAM is tighter.
--parallel 1                   # one user. For 8+ concurrent users, see section 07
                               # and prefer the non-unified KV layout.

Every sweep calls gpu_settle() between arms. It waits for the previous arm's VRAM to be released and for the card to cool, then holds a floor delay. Back-to-back arms would otherwise measure order instead of configuration.

12What this does not prove

Stated plainly, because a benchmark without its limits is marketing

  • Capping VRAM reproduces capacity, not bandwidth. A 24 GiB cap on this Blackwell card overstates a real 3090 (~1.6 TB/s vs 936 GB/s). The 5090 row is the one fair proxy. Multi-GPU rows are an optimistic upper bound — one capped pool is not two cards.
  • Most long-context cells are a single run. Short-prompt arms repeat to 0.2% decode and 0.7% prefill, but a 245,760-token cell costs about 18 minutes and ran once.
  • The mmap penalty is measured, not explained. The two mmap passes agree within 0.5%, so the file cache is not the obvious cause. A background model download ran during that control at about 54 MiB/s mean disk read; both mmap passes shared it.
  • The recall test restarts the server once per document length. Only the first probe after each start runs on a never-used server; later probes run on a server that has already served requests.
  • The speculation gain is about +7% with a wide interval (+0.6 to +11.0 tok/s, 95%) from four runs per arm. Draft acceptance also declined across the runs, 43% → 28%, and we do not know why.
  • The preserved-reasoning comparison is one run per arm. It shows the direction and the mechanism, not a settled magnitude.
  • The microbatch sweep covered one configuration: context 32,768, no expert offload, this card. Small-card and long-context behavior is unmeasured.
  • Quant quality was never measured. IQ4_XS versus Q4_K_XL is a speed and reach comparison only.
